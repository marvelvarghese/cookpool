# spliteco-worker — architecture

- **One ledger.** Rows go into `kitchen_txns` and `kitchen_txn_splits` (migration 220) with Spliteco's columns from migration 530 (`app`, `bucket`, `category`, `revises`, `moved_from`, `deleted_at`, `split_spec`), through `@saas/db/spliteco`, which applies the same Σpaid = Σowed = total check and the same currency guard as kitchen-worker's statements.
- **Append-only.** Edit = reversal + new version (`revises`); delete = reversal stamped `deleted_at`, restorable for 30 days by a new version that `revises` it; move = reversal in group A + new version in group B (`moved_from`). Each is one D1 batch with its `spliteco.expense.*` audit event. Partial unique indexes on `reverses`, `revises` and `moved_from` stop two concurrent changes of one version.
- **Maths.** `@saas/kitchen-engine/splits` splits an expense six ways (equal, exact, pct, shares, adjust, items) with the largest-remainder rule; balances and plans are `@saas/kitchen-engine/ledger`'s `balances`, `pairLines` and `settlePlan` over every row of a group, exactly as kitchen-worker computes them. Kitchen groups keep two balances (`bucket` kitchen / other), each worked out on its own rows.
- **Authorization.** Every group read or write takes membership's facts and policy-worker's decision; a denial is the opaque 404. Cookpool's rows (`app = 'cookpool'`) are read-only here (409 `owned_by_cookpool`).
- **Settling up (SE2).** A payment is settlement rows on the same ledger — one per balance it pays, a kitchen group's Kitchen first, then Other (or as the payer splits it), linked by `source_kind = 'payment'` and one `source_id` — written in one batch with `spliteco.settlement.recorded`. The caller is always the payer, and a payment may not exceed what the group's plan (`@saas/kitchen-engine/settle`: the fewest payments, or pair by pair when the group switched simplify debts off) says they owe the payee in each balance. "Not received" is the payee's alone: it reverses every row of the payment with `spliteco.settlement.not_received`. Neither is taken through a delegation.
- **Reminders and profiles (SE2, migration 540).** `ledger_reminders` holds one row per reminder; a second one for the same pair inside 24 hours is 409 `reminded_recently`. It is written with `spliteco.reminder.sent`, then sent through notifications-worker (`@saas/notifications-client`). `spliteco_profiles` holds UPI IDs, shown only to people who share a group; `spliteco_group_settings` holds simplify debts (default on), kept out of `kitchen_group_settings` so switching it never pins a group's currency.
- **Live split (SE4, migration 550).** `ledger_live_sessions` holds an itemized draft (JSON) with an 8-character join code; `ledger_live_claims` who had which item (an item share's mode and value); `ledger_live_presence` who last polled. Only group members read a code (anyone else gets the opaque 404); a member claims only for themselves, the opener for anyone. No money moves until the opener locks it, once every item is claimed: the expense goes through the same parse, engine split and member check as `POST /groups/{org}/expenses`, and is one batch with `spliteco.expense.added`, `spliteco.live.locked` and the session's state (`idem_key = live_<session>`, so a second lock replays). Claims are guarded in SQL by the session being open and inside its 24 hours.
- **Assistants (SE5, migration 560).** A request api-edge forwards with a delegation (`x-actor-delegation-id`, its scopes and the assistant's name) reaches a handler only when `src/delegated.ts` lists its route for one of those scopes: money.read's reads, and money.write's drafts, draft saves, delete, restore, comments and reminders. Payments, "not received", the profile and the settle plan are 403 `not_from_an_assistant`; the add, edit and move routes themselves are 403 `draft_required`; anything else is 403 `scope`. An assistant drafts (`POST /drafts`: the split as it would save, kept in `ledger_drafts` for 10 minutes, the person's and the delegation's only) and saves only on the person's yes (`POST /drafts/{drf}/save`), which runs the ordinary handler with the draft's token as its idempotency key — every check again, and a second save replays. Every row an assistant writes carries `via_delegation` and `via_client` (its name), so Activity says "via Claude". Every add, edit, delete, restore and move (an assistant's or not) sends `spliteco.expense_for_you` to everyone on the expense but the actor, after the write and best-effort ("Anu via Claude …"); Cookpool's rows are never told about here. `GET /me/search` finds current expenses by words.
