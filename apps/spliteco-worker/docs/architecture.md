# spliteco-worker — architecture

- **One ledger.** Rows go into `kitchen_txns` and `kitchen_txn_splits` (migration 220) with Spliteco's columns from migration 530 (`app`, `bucket`, `category`, `revises`, `moved_from`, `deleted_at`, `split_spec`), through `@saas/db/spliteco`, which applies the same Σpaid = Σowed = total check and the same currency guard as kitchen-worker's statements.
- **Append-only.** Edit = reversal + new version (`revises`); delete = reversal stamped `deleted_at`, restorable for 30 days by a new version that `revises` it; move = reversal in group A + new version in group B (`moved_from`). Each is one D1 batch with its `spliteco.expense.*` audit event. Partial unique indexes on `reverses`, `revises` and `moved_from` stop two concurrent changes of one version.
- **Maths.** `@saas/kitchen-engine/splits` splits an expense six ways (equal, exact, pct, shares, adjust, items) with the largest-remainder rule; balances and plans are `@saas/kitchen-engine/ledger`'s `balances`, `pairLines` and `settlePlan` over every row of a group, exactly as kitchen-worker computes them. Kitchen groups keep two balances (`bucket` kitchen / other), each worked out on its own rows.
- **Authorization.** Every group read or write takes membership's facts and policy-worker's decision; a denial is the opaque 404. Cookpool's rows (`app = 'cookpool'`) are read-only here (409 `owned_by_cookpool`).
