### AI1 — AI plumbing and sentence parsing in the server (AI-2)

**Built.**
- **The client** (`apps/kitchen-worker/src/ai/`): `@anthropic-ai/sdk` 1.3.0 (pinned, more than two weeks old) behind an `AiProvider` interface (`provider.ts`; tests stub it through `KitchenDeps.aiProvider`). `runner.ts` runs one `AiTask` — fixed system prompt + fixed reference block, both `cache_control: ephemeral`, then the task's user content, `output_config: { effort: "low", format: { type: "json_schema", schema } }` — on `claude-haiku-5-5`, checks the stop reason, the JSON against the schema (`schema.ts`) and the task's own `check`, and only when that fails (or the answer stopped at `max_tokens`) sends the same request once to `claude-sonnet-5-5`. A refusal, a thrown provider error or a second failed check is `ai_failed`; provider messages never reach a caller. `thinking` is left at the models' default (adaptive). The SDK client runs with `maxRetries: 1`, `timeout: 30 s`. AI-3…AI-6 add an `AiTask` each beside `uses-task.ts` and a route in `ai-routes.ts`.
- **The secret**: `ANTHROPIC_API_KEY` in kitchen-worker's `component.yaml` exactly as notifications-worker's `VAPID_PRIVATE_KEY` (`optionalSecretEnv: secret://ws_QX130J0D/cookpool/{{ .environment }}/ANTHROPIC_API_KEY` + `runtimeSecrets: "ANTHROPIC_API_KEY"`); never a var (the template carries a comment only; `tests/config-worker` pins both). No value was set.
- **Migration 470 `470_kitchen_ai`**: `kitchen_ai_usage (id, user_id, feature, model, input_tokens, cached_tokens, output_tokens, audio_seconds, ok, created_at)`, `feature` CHECK in `uses, receipt, recipe_import, transcribe, ask_step, swaps, idea`, counts ≥ 0, `ok` 0/1, index `kitchen_ai_usage_user_idx (user_id, created_at)`. Repository `createAiUsageRepository` in `packages/db/src/kitchen/ai.ts` (`recordAiUsage`, `aiUsageBetween`).
- **Routes** (contracts in `packages/contracts/src/kitchen-ai.ts`, also `@saas/contracts/kitchen-ai`; api-edge already forwards `/v1/kitchen/…`, no edge change):
  - `GET /v1/kitchen/me/ai` → `{ available, features: { sayIt, receipt, import, voice, swaps }, today: { actions, actionsLimit: 50, voiceSeconds, voiceSecondsLimit: 1800 } }`. Answers without a key (`available: false`, every feature false). `sayIt` is the only feature true with a key; each later task turns its own on (`SERVER_FEATURES` in `handlers/ai.ts`).
  - `POST /v1/kitchen/me/ai/uses { text }` (1–300 chars trimmed) → `{ lines: AiUseProposal[], unsure: string[] }`, where `AiUseProposal = { itemRef: { kind: "personal", itemId } | { kind: "group", orgId, itemId }, name, pantry: PantryRef, quantity, unit? | measure?, consumers: usr_[] (caller first), label, flags: ("the_rest" | "people_removed")[] }`. Order: 503 `internal_error` `ai_unavailable` without a key (before the body is read) → 422 on the body → 429 at the limit → reads → model. Writes nothing.
  - Errors: 503 `internal_error` + `details.reason: "ai_unavailable"`; 429 `rate_limited` + `ai_daily_limit` (or `voice_daily_limit`) with `details.limit`, `used`, `resetsAt` (next UTC midnight); 502 `internal_error` + `ai_failed`. Reasons in `KITCHEN_AI_ERROR_REASONS`; no new error codes.
- **Limits**: 50 actions (every feature but `transcribe`) and 1800 voice seconds per person per UTC day, counted from `kitchen_ai_usage` before the call; failed actions count. One usage row per action.
- **Say what you used**: the model gets the caller's usable items with something left (`searchItems`, ≤ 100) as `{ ref: "iN", name, pantry: "mine" | "gN", unit, left, measures: [one…] }`, pantries as refs, and people as `me` + `person N` with a first name and their shared pantry refs (≤ 40). The check fails the answer (→ Sonnet) on an unknown item or person ref, no people, both/neither unit and measure, a unit of the wrong dimension, a measure the item lacks, or an amount ≤ 0. Then it fixes what the sentence may really say: more than is left → the rest in the item's unit (`the_rest`); a named person not in the item's group, or anyone but the caller on a personal item → left out (`people_removed`); a group line nobody left can have is dropped and the names go to `unsure`. Measures said in the plural are accepted and counts are rounded to halves. The model's `unsure` words are trimmed, de-duplicated, at most 10.

**Departures from the design.**
- **No `kitchen_ai_imports`** (owner's scope change during AI-2): recipe import will be from a photo only — no links, no pasted text — so the shared URL cache is not needed; migration 470 has `kitchen_ai_usage` only. AI-4's task and design §4 still describe links/text and the cache; AI-4 should follow the new scope.
- **One usage row per action**, not per model call: a Sonnet retry's tokens are summed into the action's row and `model` is the last model called. Spend per model is therefore approximate for escalated actions.
- **Limits are soft**: the count is read before the call, so concurrent requests at the 50th action can each run (a person may end a day an action or two over).
- **First names**: the first run of letters of the person's display name, else of their email's local part (`kiran.rao@…` → `kiran`); a person with neither is not sent and cannot be named. Item names are sent as the user typed them.
- **`ai_failed` is 502** and `ai_unavailable` 503, both on the pinned `internal_error` code.
- **A sentence with nothing usable** returns `{ lines: [], unsure: [] }` without calling the model and without counting an action.
- **Proposal shape**: the design's `itemRef` is the console's item ref (`{ kind, orgId?, itemId }`), plus `flags`. Ask-first items (PN-8) are proposed like any other; the console's use call will meet `ask_first` as it does today.
- **Caching**: the system prompt and the units reference are cached, and so is the caller's pantries block (third breakpoint). The food list (RC-3) is not sent for this task — it is not needed to read a use. Haiku's minimum cacheable prefix may be larger than this prompt, in which case the cache silently does not apply.
- `voice_daily_limit` and `audio_seconds` exist and are tested at the helper level; the transcription route that uses them is AI-5's.

### AI2 — receipts in the server (AI-3)

**Built.**
- **Route** (`apps/kitchen-worker/src/handlers/ai-receipt.ts`, one entry in `ai-routes.ts`; contracts in `packages/contracts/src/kitchen-ai.ts` "Receipts (AI-3)"; api-edge already forwards it, no edge change): `POST /v1/kitchen/me/ai/receipt { image }` → `AiReceiptResponse = { store?, total?, currency, sumMinor, totalMatches, lines: [{ text, name?, foodId?, quantity?, unit?, priceMinor?, pantry?: PantryRef, fromItemId?: itm_…, confidence: "sure" | "check", reason? }] }`. Order: 503 `ai_unavailable` (before the body is read) → 422 on the photo → 429 `ai_daily_limit` → the caller's groups, restock names, item history (≤ 500 names) and group currencies → the model → the food list for the lines (ONE read) → local matching. Writes nothing but the usage row; one action counted (feature `receipt`, failed ones too). `SERVER_FEATURES.receipt` is now true.
- **The photo**: base64, a `data:…;base64,` prefix and whitespace dropped; the type is sniffed from the first bytes (JPEG `FF D8 FF`, WebP `RIFF…WEBP`) — the prefix's type is ignored; size from the base64 length, ≤ `AI_RECEIPT_MAX_BYTES` = 1 572 864 (1.5 MB). Refusals are 422 `validation_failed` with field errors on `image` ("Must be a photo, in base64", "Must be a JPEG or WebP photo, in base64", "Must be at most 1.5 MB"). Only the first 12 bytes are ever decoded. The image is held in the request only: it is not stored, logged, written to audit or usage, and a provider error's text is never logged or returned.
- **The read** (`ai/receipt-task.ts`, `RECEIPT_TASK`): Haiku first, Sonnet once on a failed check, via AI-2's runner. User content = `[image block (base64, its media type), "Read this receipt."]`; the system prompt and a units reference are cached. The model is sent nothing about the caller. Strict schema: `{ store, date, time, total, lines: [{ text, name, quantity, unit (unit key enum), priceMinor (integer paise), isFood }], adjustments: [{ text, amountMinor }] }`. The prompt's rules: the charged price never the MRP, multipliers (`2 X 68.00`, `×2`, a qty column) applied to the amount and the line total, weights/volumes (`1KG`, `500G`, `1L`, `200ML`, weighed lines), plain names ("MLK PNR 200G" → Paneer), isFood, and GST/discount/round-off as `adjustments`, never lines — with an included GST summary or "you saved" NOT an adjustment. The check (→ Sonnet): every line has text; prices and the total are whole non-negative paise; a quantity and its unit come together, the quantity > 0 and parses in the unit (`toMilli`). At most 60 lines (`AI_RECEIPT_MAX_LINES`).
- **Matching** (`ai/receipt-match.ts`, no model): the pool is the restock read's newest purchase per name and pantry plus the item history's newest per name (deduped). A line matches a purchase by folded name (case, punctuation, plural s/es) first, else by the same food (both looked up through the food list: "Pyaz" ↔ "Onions"). `sure` only when the line is food, has an amount, and the newest match counted in the same kind of unit (count/mass/volume/pack) has a price within ±50% of the line's for the same amount — or, with no match or a match with no price, when the name (else the printed text) is exactly a food on the list and the unit's kind fits it (a food with a piece weight takes count and mass). Else `check` with a reason: `not_food` (`AI_RECEIPT_NOT_FOOD`; no pantry, food or item), "no amount on the line", "bought in ml before", "price far from last time's", "not sure what <text> is", "<Food> isn't counted in <unit>", "no price from before". The pantry is the newest match's that the caller can add to (with that purchase as `fromItemId`); else their most-used addable pantry for the food's category (by history `times`), else most-used overall, else their own — with the newest match as `fromItemId` when there is one (the purchases route takes any reachable item). A matched line's `name` is the caller's own spelling.
- **Totals**: `sumMinor` = the food lines' prices; `totalMatches` = a total was printed and every line (food or not) plus the adjustments meets it within 1 paisa — or every line alone does (a GST summary misread as an adjustment). `currency` = the chosen pantries' (group settings; INR for the caller's own), the most lines'; INR when none.
- **DB**: `matchFoods(names)` on the kitchen repository (`packages/db/src/kitchen/foods.ts`): matchFood for many names in ONE read (`json_each` + the same `nameMatchSql`), keyed by the name as given. No migration.
- **SDK**: `kitchen.aiReceipt(image)` in the "Cookpool AI (AI-2)" section; types and constants re-exported from the index.

**Departures from the design.**
- **Response additions**: `currency`, `sumMinor`, `totalMatches` (owner's brief). `total`'s difference is reported through these, not a separate field. `pantry` is a `PantryRef` (as the restock lines'), not the purchase line's `"personal" | org_…` string.
- **Date and time** are read by the model (schema) but not returned: purchases are always bought today, and the design's shape has no date. Adding `date?` later is additive.
- **No food list in the prompt**: the model names items in plain words and the server matches them against the food list's names and aliases; the food list (design §1's cached block) is not sent. AI-2 made the same call for say-what-you-used.
- **Adjustments** (GST added, discounts, round-off, fees) are read so the total can be checked, but not returned.
- **Food answers** ("Is Kanda onion?", per pantry) are not consulted by the matcher: names match through the shared names table only, as `matchFood` does.
- **"Most-used pantry for the food's kind"** uses the item category (the food's category, else the matched purchase's), weighted by the history's `times` per name (attributed to the newest record's pantry).
- No `category` on a line: AI-8 fills it from the food (`foodId`) or last time's item when it builds the purchase lines.

### AI2 — receipt scanning in the shopping run (AI-8)

**Built.** Console only, behind `newFrame()` (design §3, the canvas's AiReceipt and rule 13's AI look). No route, no migration, no contracts change. It reads AI-2's `GET /v1/kitchen/me/ai` (`kitchen.ai()`) and AI-3's `POST /v1/kitchen/me/ai/receipt` (`kitchen.aiReceipt(image)`, types and `AI_RECEIPT_NOT_FOOD` from `@saas/contracts/kitchen`), and writes through PN-3's `buy()` / `undoPurchase()` as PN-6's run does. The SDK methods were first written here to the design's shape and deleted once AI-2 (#97) and AI-3 (#99) landed theirs: the SDK has no AI-8 diff.

- **Where it shows** (`receiptScanShows`, `useReceiptScanShows`): the new frame, `available`, `features.receipt`, and this device's "Scan receipts" switch on. Two entry points: **Scan a receipt** at the top of `/pantry/run` (with the ✨ Cookpool AI chip and the gradient edge), and a camera (44 px, gradient edge) beside the Pantry's **+ Bought**, which opens `/pantry/run?scan=1` → the camera at once (the flag then leaves the address). The status read runs only in the new frame with the switch on; while it loads or fails, nothing shows.
- **The switches** (`lib/ai-switches.ts`): `<storagePrefix>.ai-switches` in localStorage holds the ones turned off (`{"receipt":false}`); every feature is on otherwise. `useAiSwitch`, `setAiSwitch`, `parseAiSwitches`. AI-7's settings page turns them (AI-8 only reads `receipt`).
- **Capture** (`ReceiptCapture`): the dark full-screen step — Close, "Scan a receipt", the corner guides, "Fit the whole bill · flat, in good light", the 76 px shutter (`<input type="file" accept="image/*" capture="environment">`) and Photos (the same input without `capture`). Escape closes. Close goes back to the run, or to the Pantry when it came from the camera there.
- **The photo** (`receipt-image.ts` pure, `receipt-photo.ts` browser): decoded with `createImageBitmap(…, { imageOrientation: "from-image" })` (an `<img>` on older Safari), turned by EXIF orientation on the canvas only when the decoder visibly didn't (a quarter turn decoded at the stored size; `readJpegMeta` reads the APP1 orientation and the frame size), drawn at 1200 px on the long side (never enlarged), JPEG at 0.8, then 0.7, 0.6, 0.5, then the long side × 0.8 (960, 768, 614) with each, until its base64 is ≤ 1,500,000 characters. Sent without the `data:` prefix.
- **Reading** (`ReceiptReading`): the chip, "Reading your receipt…", the photo under a sweeping green→cook-colour line, "Reading the lines…" then "Found 6 lines · matching to your pantries…", three shimmering rows (still under reduced motion), and Cancel (aborts the request; back to the camera).
- **The categories.** AI-3's lines carry none, so while "matching to your pantries…" shows (at least 600 ms) the console reads, in parallel, each line the restock read doesn't already know: its `fromItemId` item (`getPersonalItem`/`getGroupItem` in the line's pantry), else its `foodId` food (`foods({ q: name })`, matched by key). A failed read leaves "other". Non-food lines need none.
- **The result** (`receiptRun`, `ReceiptResult`): the run, filled. Header ✕ · ✨ Cookpool AI · Shopping run; the receipt card (the photo, "DMart · today 6:40 pm", "6 lines · bill ₹642", and "Lines add up to the bill ✓" or "₹95 of the bill isn't ticked" / "₹12 more than the bill" in amber); **MATCHED · N** (sure, food: ticked, gradient edge); **CHECK N** (food not sure: "Is this Paneer · 200 g · ₹95?" with **Yes, paneer** and **Change**; a nameless line asks "What is this · ₹20?" with **Name it**); "1 non-food line left out · Dish soap ₹44 · Show". Each row shows the printed text in small monospace above "Milk · 2 L", the pantry chip and the price; tapping a row opens PN-6's editor (the same − / +, price box and pantry chips, now `RunLineEditor` in `run-line-editor-ui.tsx`). Change opens a name box too. Footer and **Add N · ₹total** are the run's own, and Add is `useShoppingRun` (one `POST /purchases`, toast "Added 5 to your pantries · ₹598 · Undo").
- **A line in the run's model:** `last` is the receipt's own amount, unit (spellings like KG, ltr, nos, pkt read as kitchen units; else last time's; else pcs) and price, in the receipt's `currency`. The ladder starts at the receipt's amount and the price scales from the receipt's. Its pantry is the line's (else its restock line's, else yours). `fromItemId` is sent only when the server matched one. The waste rule and use-by gap are last time's only when the line matches a restock line in the same pantry; otherwise neither is sent and the server copies `fromItemId`'s. A line without a price starts with an empty box ("Price for Curd").
- **Refusals** (`receiptError`): `ai_unavailable` (or a bare 503) → the status is marked unavailable at once, so both entry points hide, and the page says "AI isn't set up yet · add by hand" with **Add by hand**; `ai_daily_limit` (any 429) → "You've used today's AI scans · try tomorrow" with **Add by hand**; anything else, a receipt read with no lines, or the network → "Couldn't read this receipt · Retake or add by hand" with **Retake** and **Add by hand**. A photo that can't be decoded or made small enough goes back to the camera with "Couldn't use this photo · try another".
- **Shared files, all additive:** `shopping-run.ts` (`RunSource` instead of `RestockLine` for a line's source, optional `RunLine.receipt` and `RunPick.name`, `TickedLine.name`, "A name for …"; a restock line sends exactly what it did), `shopping-run-ui.tsx` (the scan's phases around the run; the editor moved out), `pantry-new-ui.tsx` (the camera), `query-keys.ts` (`kitchenAiStatus`, not under `kitchenPantry()`). New: `receipt-run.ts`, `receipt-image.ts`, `receipt-photo.ts`, `receipt-data.ts`, `receipt-scan-flow.ts`, `receipt-scan-ui.tsx`, `receipt-run-ui.tsx`, `run-line-editor-ui.tsx`, `lib/ai-switches.ts`.
- `console-artifact.mjs build`: `/pantry/run` and `/pantry` stay static (○); 38 pages as files, 17 `_redirects` rules.

**Departures and decisions:**
- **The bill check counts the non-food lines left out as on the bill** (the brief says "the sum of ticked lines"). Otherwise every receipt with dish soap on it would read short. A non-food line ticked after Show counts once. When AI-3 says the lines reconcile with the total through the receipt's own adjustments (`totalMatches`: tax, discount, round-off), that adjustment counts as on the bill too. Lines moved to a pantry in another currency are left out of the sum.
- **The result shows only the receipt's lines**, not FINISHED / RUNNING LOW / YOU USUALLY BUY under them (the canvas does this). Add by hand returns to the plain run.
- **Rows are compact until tapped** (the canvas's row: text, name · amount, chip, price); tapping opens PN-6's editor. Ticked lines in PN-6's own run open their editor at once, as before.
- **"Found N lines" shows for at least 600 ms**, while the categories are read; the count isn't known until the read is back.
- **A pantry the caller can't add to falls back to theirs** rather than locking the line (AI-3 says it never sends one).
- **The size limit is stricter than the server's:** base64 ≤ 1.5 M characters (≈ 1.1 MB decoded) against AI-3's `AI_RECEIPT_MAX_BYTES` decoded. A 1200 px receipt is ~150–550 KB, so it doesn't bite.
- **The switch storage is AI-8's** (`lib/ai-switches.ts`, key `ai-switches`, default on). AI-7 should build its settings on it rather than a second store.

**Prompt caching.** Measured from the prompts (≈ 4 characters a token): say-what-you-used's system + units reference ≈ 450 tokens, the receipt's ≈ 800 (each plus the output schema). Both are below any Haiku minimum cacheable prefix (1,024 at the least; earlier Haikus needed 2,048–4,096 — the SDK 1.3.0 types don't state Haiku 5.5's), so the fixed blocks are **not** cached in practice. Say-what-you-used's third breakpoint (the caller's pantries block) can carry the prefix over the minimum for a large pantry (roughly 60+ items); the receipt's image sits after the last breakpoint and is never cached. `cache_control` is left in place (harmless); the prompts were not padded. The cost estimates below therefore assume no cache reads.

**Estimated cost** (Haiku only, escalation off, no cache):
- **A receipt**: input ≈ 800 prompt + ≈ 300 schema + ≈ 1,200–1,600 image (the console's 1,200 px photo) ≈ 2,600 tokens → 260 µ$; output ≈ 660 for 20 lines → 330 µ$. **≈ $0.0006 typical**, at most ≈ 2,700 × 0.10 + 1,700 × 0.50 ≈ **$0.0011** at the 1,700 cap. (A Sonnet retry of the same read would have added ≈ $0.012, twenty times the read.)
- **A sentence**: input ≈ 450 prompt + ≈ 200 schema + 500–2,500 pantries + the sentence ≈ 1,200–3,200 tokens → 120–320 µ$; output ≈ 120 for 2–3 lines → 60 µ$. **≈ $0.0002 typical**, at most ≈ 320 + 600 × 0.50 ≈ **$0.0006** at the 600 cap.
- **The budget**: $5 a month is ≈ 8,000 receipts or ≈ 25,000 sentences at typical sizes. One person at every cap for a day (10 receipts + 40 sentences) is at most ≈ $0.036.

**Departures from the design.**
- Design §1's "retry once on Sonnet if validation fails" is now opt-in (`AI_ESCALATE=on`); by default a failed receipt read degrades to `check`/`unclear` lines and a failed sentence is `ai_failed`.
- **The budget refusal** is `details.reason: "budget"` on 503 `internal_error`, not `ai_unavailable` (owner's brief). The console's receipt scan (AI-8, `receiptError`) maps only `ai_unavailable` and 503-without-reason to "unavailable", so a `budget` 503 shows its generic "Couldn't read this receipt" until the console learns `budget`; `ai()`'s `available: false` already hides the button on the next status read.
- **Cache writes** are priced at the input rate (the table has no write price); real 5-minute cache writes cost 1.25× input, so an action that writes the cache is slightly under-estimated. With the prefixes below the minimum (above), writes are rare.
- `AiStatus.budget` and `today.receipts` / `receiptsLimit` are optional in the type (always sent) so payloads built before AI-13 — the console's tests — still type-check.
- One usage row per action stays: an escalated row's `cost_micros` is both calls' sum, its `model` the last one.
